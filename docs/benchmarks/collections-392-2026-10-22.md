# Standalone collection and metadata comparison, 2026-10-22

Map-projection medians decrease 36–51% versus preceding StreamFusion across Flink
2.2.1 and 1.18.1. On 2.2, width-64 BIGINT reverse and prepend beat both prior
StreamFusion and paired stock with nonoverlapping measured ranges. Keys/entries
remain 25–34% slower than stock; ROW construction remains slower too.

The final string exit borrows bytes during an ownership copy into generic rows.
JOIN beats paired stock on both lines; TYPEOF sampled exit allocations decrease
38–42%. Timing ranges and stock-control drift limit claims about a distinct
metadata throughput gain. These improve the existing default-enabled extension,
whose standalone regressions were accepted on 2026-10-17.

[Collection techniques](../optimizations/collection-representation-work.md),
[the string exit boundary](../optimizations/zero-copy-exit-transpose.md#synchronous-copies-of-cache-free-scalar-strings)
and [query admission](../operators/calc-filter.md#collection-expressions) describe
the current implementation and its representation guards.

## Method and provenance

Actual preceding Java production code is frozen at `d951a838`. Collection/BIGINT
cohorts use implementation `3c47a89d`; the final string cohort uses `f7867f55`, which
replaces binary string packing with synchronous borrowing for generic-row copies.
The temporary diagnostic commits change only their runner, benchmark assertions
and the recorded implementation. The same instrumented benchmark and metrics
helper are compiled against each revision on each released Flink line. Native
source is unchanged within these comparisons; each cohort pair uses one identical
release core DSO built with `--no-default-features --features mimalloc`.

Each expression/cohort starts a fresh JVM. Stock/native order alternates within it:
two warmup pairs and five measured pairs, two million source rows, parallelism one,
a 2 GiB heap, 1,024-row batches and Temurin 17.0.20.1 on an isolated Ubuntu 24.04
runner. Cluster construction and the initial explain are outside timing.
Execution-time planning, deployment, runtime source construction, both row/Arrow
transposes, production JNI/IPC and the rowwise blackhole sink remain inside.

MAP input has three non-NULL BIGINT values keyed by `a`, `b`, `c`, with a NULL map
every eighth row. NULL keys/values and other admitted value types are correctness
checks, without a type-wide performance claim. Numeric source arrays have width
8/64 and a value domain equal to that width. STRING arrays cycle over eight values
with 64-byte suffixes. Array parents are NULL every eighth row and element indices
divisible by seven are NULL. Constructor/TYPEOF controls keep the same source work
even when they do not read the array. These are low element-cardinality fixtures.

Candidate jobs require consumed NativeCalc input, both transpose plan nodes and
the expected Rust function without a JVM evaluator. TYPEOF is a folded constant,
not a per-row TYPEOF kernel. The intentionally generated MAP-constructor control
instead requires its generated MAP function. Separate profiled processes are
excluded from elapsed-time comparisons.

The initial run completed seven matched cases on 1.18 and eight on 2.2, then stopped
at an incorrect Rust-only assertion for the generated MAP constructor. The follow-up
completed those controls and profiles. Unchanged 1.18 Kafka fixtures subsequently
exposed binary string output's legacy `RowData.toString()` incompatibility; that
prototype was removed. Final JOIN/TYPEOF pairs were rerun on both engines and both
lines with generic-row output. Every completed non-string comparison stays primary;
old string prototypes and initial unpaired controls remain retained separately.
Selection is based on implementation and completion, never favorable timing.

Runner CPUs differ: initial 2.2 uses EPYC 7763, initial 1.18 Xeon Platinum 8573C,
follow-up MAP controls use EPYC 9V74/9V45, and final strings use EPYC 7763/9V74.
Every case compares both cohorts on the same runner with its own paired stock.
Do not aggregate elapsed times across these legs or attribute cross-line differences
to Flink alone. Short jobs still include startup and separate-JVM drift.

The measurements use frozen source snapshots around integration onto main `717b8d94`, whose separate
changes cover synchronization/date evaluation and an Iceberg checkpoint fixture.
Collection/BIGINT and final generic-string routines remain the same on integration;
these recorded binaries do not measure the combined main revision.

## CPU and allocation profiles

Matching previous/candidate JVMs use async-profiler 4.6, CPU sampling at 1 ms and
Java allocation sampling at 1 MiB, two million rows, one warmup pair and one
separate diagnostic pair. Profiled durations never enter elapsed-time comparisons.
The process includes setup, planning and stock jobs; scopes below select native
operator stacks. Counts are inclusive and overlap. Allocation weights estimate Java
allocated bytes, not copied bytes, retained memory or native heap totals; GB is 10^9 bytes.

| 1.18 / mapvalues / NativeCalc | 1,587 | 406 | 5.560 | 0.870 |

| 1.18 / typeof / exit | 632 | 522 | 1.672 | 0.971 |

MAP_VALUES JVM expression upcalls fall from 1,994 samples to zero on 2.2 and 1,029
to zero on 1.18; MAP_ENTRIES falls from 4,265 and 2,370 to zero. The outer production
JNI/C Data boundary remains. Its preceding inclusive stack also contains JVM
callback work, so these counts do not isolate JNI transition costs. Value-only MAP
projections remove the nested string writer because the keys' caches are unobserved.

Reverse64 BIGINT writer samples fall from 952 to 549 on 2.2 and 620 to 295 on 1.18.
Whole-NativeCalc estimated allocations do not improve: 1.578 to 1.582 GB and 1.467
to 1.588 GB, respectively. Reserving capacity targets writer CPU; rowwise array
copying remains. MAP_ENTRIES still spends 2,594/1,346 inclusive samples in its exit.

The final generic-row TYPEOF exit reduces sampled Java allocations by 38.2% on 2.2
and 41.9% on 1.18. It removes an intermediate owned UTF-8 buffer while retaining the
required generic-row copy. This is a measured allocation reduction, not proof of
sustained metadata throughput.

## Limits and rejected work

The 2.2 width-64 reverse and prepend native ranges are below both paired stock and
preceding native ranges. Short reverse, ARRAY and MAP_VALUES ranges overlap their
stock controls, so their favorable medians are weaker evidence. On 1.18, both reverse
widths still lose to stock despite improving preceding StreamFusion. ROW medians
increase by 2–3% versus preceding code; the 2.2 ROW stock control shifts by about
12%, and both native ranges overlap. The 1.18 ARRAY control regresses by 5.9% with
overlapping ranges. No constructor-wide speedup is established.

A generated binary-exit prototype for collections increased width-64 reverse and
prepend medians and did not materially improve MAP construction. It was removed;
[the rejection](https://github.com/datafusion-contrib/StreamFusion/blob/main/.claude/wontdos/collection-binary-exit-projection.md) and
[all exploratory trials](results/collections-392-2026-10-22/exploratory.json) retain
that attempt. The intermediate map-view pass overlapped an integration workload and
is diagnostic only. None of those local runs enters the primary comparison.

The MAP constructor remains 44–53% slower than stock, with overlapping prior/current
ranges. Final JOIN beats paired stock with nonoverlapping ranges on both lines, but
its 2.1%/1.7% reductions versus prior code have overlapping ranges. TYPEOF medians
change by -0.9%/-6.8% versus prior code; ranges overlap, including a high 2.2 native
outlier. Its stock controls shift by -1.6%/-0.7%. Favorable medians and lower sampled
allocations do not establish an isolated metadata throughput gain.

Binary string packing was also removed after unchanged Kafka fixtures exposed
legacy `RowData.toString()` incompatibility. Its earlier JOIN/TYPEOF timings remain
in the follow-up JSON, excluded from primary summaries. The
[scoped rejection](https://github.com/datafusion-contrib/StreamFusion/blob/main/.claude/wontdos/scalar-string-binary-exit.md)
records why typed parity and ownership alone were insufficient.

The surviving key/entry losses include required UTF-16 transport and rowwise output
materialization. No broad JNI redesign is inferred from these standalone jobs;
the separate [bounded native-boundary investigation](../optimizations/calc-schema-once-c-data.md#cache-calc-output-schemas)
retains an output-schema cache and defers broader ownership redesign. It does not
remeasure or resolve these workload-specific losses.

## Validation

The final focused correctness suite passes 345 checks on Flink 2.2.1 and 308 on
1.18.1 with 37 release-specific skips. It covers the six admitted map value types,
NULL/empty maps, NULL keys/values, hash collisions, malformed UTF-16, generic and
binary inputs, composed-consumer and unverified-boundary guards, ownership after
source mutation and batch closure, IPC, buffer growth, object reuse and row kinds.
Wide decimals and full-range timestamps remain owned in represented scalar ROWs.
The string ownership checks also assert generic row rendering, preserving the released
legacy RowData consumer behavior that exposed the binary-packing prototype.
The diagnostic route assertions are also exercised with small generated-MAP and
Rust-MAP_VALUES jobs on both lines; their times are not performance observations.

## Reproduction

Build the release core before timing, then run from the repository root:

```sh
cargo build --manifest-path native/Cargo.toml -p streamfusion --release \
  --no-default-features --features mimalloc
SF_BENCHMARK=true mvn -pl streamfusion-runtime test -Pbench \
  -Dnative.build.skip=true -Dnative.test.resource.skip=true \
  -Dtest=DynamicCollectionBenchmark '-Dsf.extraJvmArgs=-Xmx2g' \
  '-Dcollection.expression=MAP_VALUES(m)' -Dcollection.map=true \
  -Dcollection.rows=2000000 -Dcollection.warmup=2 -Dcollection.runs=5 \
  -Dcollection.rustFunction=MAP_VALUES
```

Use `-Pbench,flink-1.18` for that release line. The raw records retain each expression,
source type and width; array STRING cases also set `-Dcollection.bytes=64`.
The MAP-constructor control sets `-Dcollection.generatedFunction=MAP` in place of the
Rust-function assertion. TYPEOF has no runtime function assertion, but still requires
consumed NativeCalc work. Preceding controls compile the same benchmark and metrics
helper against frozen `d951a838`; only the helper sources are overlaid, leaving its
production code intact. Use the same release library in both cohorts because native
source is unchanged. Keep other builds and tests off the timing runner.
